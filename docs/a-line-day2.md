# A 线冲刺第 2 天：赛程编辑与并发保护

更新日期：2026-10-03。接续 10 月 2 日的七天冲刺计划，今天完成编辑事务、revision 重置、version 乐观锁、48 小时拉红、requestId 幂等和编辑表单。本轮按用户要求不部署到微信开发者工具或云端。

## 本地已实现

- `ScheduleManager.saveMatch` 编辑分支：事务内重读用户、启用队伍和比赛，校验本队归属、版本和状态；比赛已开赛/结束、归档、取消、无需跟场均拒绝修改。
- 修改开始/结束时间、地点或切换 TBD：清空三个跟场快照字段，revision/version 各递增一次；TBD 时间存 null，确定时间按全员没空或 `<48h` 拉红规则重算。恰好 48 小时且未全员没空保持 pending。
- 仅修改项目、对手、后勤需求：只递增 version，保留 revision、当前状态和跟场人。
- 编辑 `requestId` 在校验旧 version 之前判断；同一人重试最近已成功的请求返回缓存结果，不重复写入。不同请求使用同一 version 只允许一个成功。
- 内部 `lastSaveOpenid/lastSaveResult` 缓存编辑返回值，DTO 不公开。只保留最近一次保存；若已有后续编辑，旧请求返回 409，要求刷新。
- 表单从 `getMatchForEdit` 回填并提交 matchId/version；页面再次显示保留草稿；弱网期间锁住原始 payload/requestId 重试；冲突时锁定保存，显式重新加载后继续编辑。
- 归档标记加入编辑 DTO，终态/已开赛只读。保留未改动时间的秒和毫秒，避免只改文字也清空跟场；自定义后勤项正常回显，需求变化保存成功后提醒私聊经理人。
- DutyManager 配套修正：当前确认以 Match 快照为准，旧 confirm/rescue/assign 不再显示为当前确认；重算重读最新时间、确认和终态，并条件更新，避免并发重算覆盖新编辑。

## 与 B 线的约定

`dutyRevision` 递增仅作为赛程基准变更标记，不引入 DutyRecord 分代，也不删除历史记录。仍采用一人一场一条 upsert；旧 decline 仍参与全员没空计算。这样保持 B 线现有模型，同时满足 A 线计划中的 revision/version 递增要求。

人数聚合在事务外读取；事务内只使用文档读取和更新。跨集合人数聚合不具备事务快照一致性，继续由 B 线读时重算兜底。此次回归覆盖 A 线编辑并发与 B 线重算/编辑交错；真实云端跨函数并发仍需后续联调验收。
